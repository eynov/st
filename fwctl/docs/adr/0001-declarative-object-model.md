# ADR 0001：声明式对象模型取代 forwards[]

- 状态：Proposed
- 日期：2026-07-31

## 背景

v1/v3 的状态用一个扁平数组表达端口转发：

```json
{"sport":"29312","dport":"29312","dip":"192.0.2.20","proto":"tcp","dest_port":"29312"}
```

每条记录内联保存目标地址。同一台落地机被转发 10 个端口，IP 就在文件里出现 10
次；`both` 协议还会把一次逻辑操作拆成两条记录。后果是：改一个 IP 要改 N 处、
无法给规则命名、无法单独禁用一条规则、无法统计单条规则的流量、删除时只能按
数组下标操作。

## 决策

用三层对象模型替代 `forwards[]`：

```text
Target   命名地址对象（一个或多个 IPv4 / CIDR），地址在全局只保存一次
Service  命名端口 + 协议对象，可被多条规则复用
Rule     引用 Target 与 Service，自身不保存地址与端口
```

规则通过 id 引用对象，不通过名字。id 创建后不可变，因此重命名 target 或
service 不会破坏任何引用。

约束：跨 target 的地址不得重复；删除被引用的对象默认拒绝，需要显式
`--cascade`。

`ports`（简单放行清单）保留为独立顶层字段，不强制用户为「开放 443」创建三个
对象。`ports` 与 `accept` 类型的 rule 渲染进同一组 nftables set，是同一底层
能力的两个入口。

## 原因

- 地址唯一存储让「换落地机 IP」变成一次编辑。
- 命名对象让规则可被引用、启用、禁用、统计、审计。
- `protocol=both` 只需一个 service，对象数相对 v1 减半。
- 引用完整性可以被校验，扁平数组的字段组合不能。

## 后果

- 迁移必须把 `forwards[]` 反解成对象图，且要证明渲染结果不变。方案与验收标准
  见 [MIGRATION.md](../MIGRATION.md)。
- 任何写路径都必须在提交前做引用完整性校验，不能只做 schema 校验。
- CLI 增加 `target`、`service`、`rule` 三组名词。`fw port` 与交互菜单保持不变，
  用户可以完全不接触新模型继续工作。
