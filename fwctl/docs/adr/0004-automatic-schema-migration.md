# ADR 0004：自动 schema 迁移，且以渲染等价性为验收标准

- 状态：Proposed
- 日期：2026-07-31

## 背景

v4 的状态结构与 v1 完全不同。已部署的机器上存在正在生效的 `state.json`，其中
保存着用户当前依赖的放行端口、转发和封禁列表。要求用户手工改写状态文件是不可
接受的：改错一处就是线上防火墙故障。

## 决策

1. `state.json` 增加 `schema_version`。缺失即为 v1，自动迁移；高于当前版本则
   拒绝加载，旧程序不得覆盖新程序的状态。
2. 迁移在加载路径上自动运行，不需要用户执行任何命令。
3. 只读命令在内存中迁移后继续执行，不写盘；只有写事务才把 v4 落盘。
4. 迁移是确定性且幂等的：对象 id 由内容哈希派生而非随机生成，时间戳取自源文件
   而非当前时刻。同一份 v1 反复迁移产出逐字节相同的 v4。
5. 迁移前自动备份，落盘走与其他写操作相同的事务，失败则保留 v1 原状。
6. **验收标准是渲染等价性，不是字段搬运的完整性。** 保留一份 v3 渲染器快照，
   对每个用例断言：v1 经 v3 渲染的 ruleset，与 v1 经迁移再经 v4 渲染的 ruleset，
   在归一化后相同。

归一化只允许消除三类已声明差异：表名变化、counter 与 comment 的增加、空 set
占位元素（`127.0.0.2` / `65535`）的移除。其他任何差异都判定为迁移缺陷。

## 原因

- 自动迁移是「升级即可用」的唯一实现方式。
- 只读命令不写盘，避免巡检、监控或误用触发状态变更。
- 确定性迁移让黄金文件比对成为可能，也让同一状态在多台机器上迁移结果一致。
- 字段级断言只能证明搬运没漏，不能证明防火墙行为没变。真正要保护的是后者。

## 后果

- 仓库需要长期保留 v3 渲染器快照作为测试固件，直到不再支持 v1 状态。
- 迁移代码不能使用 `uuidgen`、`$RANDOM` 或 `date +%s`。
- 空 set 占位元素的消失是唯一刻意的渲染差异，必须在迁移文档和测试中显式声明，
  不能作为「归一化容忍范围」被默默吞掉。
- 不提供自动降级。降级路径是恢复迁移前备份并运行 v3 渲染器，文档中给出步骤。
